# HisabMitra — Technical Decisions

Each decision records context, choice and consequences. Assumptions made where the brief was ambiguous are marked **[Assumption]**.

| ID | Decision | Rationale / consequences |
|---|---|---|
| TD-01 | Money stored as `int` paise everywhere (DB columns `*_paise INTEGER`). Parsing from text is string-based; no `double` is ever used for money. | Mandatory financial correctness. Display formatting uses Indian digit grouping (`12,34,567.89`) implemented with integer arithmetic. |
| TD-02 | Client-generated UUID v4 primary keys for all rows. | Same ID locally and in the cloud → no ID remapping during sync; offline creation is trivial. |
| TD-03 | Drift `watch()` streams + Riverpod `StreamProvider` for read models. | Live UI updates after any write; no manual refresh logic. |
| TD-04 | Riverpod without code generation (hand-written providers/Notifiers). Drift uses `build_runner`. | One code-generator instead of two; fewer moving parts. |
| TD-05 | ~~Sign-in optional, phone OTP~~ **Revised 2026-11-19:** a verified account is compulsory at first launch — name, email and mobile number required; the email is verified by Supabase email OTP (code) or link (PKCE, `hisabmitra://login-callback`); the mobile number is stored (cloud `user_profiles.phone`, E.164) but not SMS-verified. The app works offline after the one-time verification. | Owner decision: no SMS provider account, and every user should have an identity. Email verification is free with a custom SMTP sender. The master brief's "email must not be mandatory" is overridden by the owner. |
| TD-06 | Groups are local by default. A group becomes cloud-backed only when its owner taps **Share to cloud** (signed in). | Personal-first privacy; non-authenticated participants stay local records with no cloud access. |
| TD-07 | Server-side writes via `apply_group_op` RPC with idempotent op IDs and revision checks; no direct table writes from clients. | Centralises authorisation and conflict detection; RLS still guards reads. |
| TD-08 | Financial sync conflicts are never last-write-wins. Both versions are kept in `sync_conflicts`; user chooses *keep mine* / *keep theirs*. | Prompt rule 12/§25. |
| TD-09 | PDF reports are rendered with Flutter's text engine onto canvases (rasterised pages) and wrapped into a PDF with the `pdf` package. | The `pdf` package lacks Indic OpenType shaping — Gujarati conjuncts/matras would render incorrectly. Trade-off: PDF text is not selectable; CSV export provides machine-readable data. |
| TD-10 | CSV export is UTF-8 **with BOM** and RFC-4180 quoting. | Excel opens Gujarati text correctly; satisfies "Excel-compatible export". |
| TD-11 | Contact selection uses the Android system picker intent (`ACTION_PICK`, Phone content URI) through a method channel. | No `READ_CONTACTS` permission is required at all — stricter than "request only when needed". |
| TD-12 | Personal ledger model: an *entry* is either **given** (I lent → receivable) or **taken** (I borrowed → payable). Repayments are child rows. Over-repayment is rejected; the UI offers to record the excess as a separate opposite-direction entry (advance/credit). | Keeps principal out of income/expense; full repayment history; prompt §12 rule on advances. |
| TD-13 | Split methods: `equal`, `exact`, `percentage` (basis points, 1% = 100), `ratio` (integer weights ×100), `adjustment` (equal ± per-person adjustments = "unequal"). Participant selection applies to every method ("selected participants only"). Remainder paise go to participants in their stable display order. | Exact reconciliation, deterministic results, all six requested behaviours. |
| TD-14 | One payer per group expense (v1). | Keeps the data model and UI simple; multi-payer can be added later by a `group_expense_payers` table. |
| TD-15 | Settlement suggestions: greedy max-creditor / max-debtor matching with ties broken by member ID. | Deterministic, ≤ n-1 transfers, easy to test. |
| TD-16 | App settings stored in Drift `app_settings` (key/value). | Settings are included automatically in backups; one storage mechanism. Secrets (session, AI key) go to secure storage, never this table. |
| TD-17 | Backups: ZIP containing `database.sqlite` (via `VACUUM INTO`), `attachments/`, `manifest.json` (schema version, app version, SHA-256 per file). Optional AES-256-GCM encryption with PBKDF2-HMAC-SHA256 (210 000 iterations) key derivation. | Consistent snapshot; integrity verification before restore; password never stored. |
| TD-18 | Automatic backup runs as a due-check on app launch/resume (daily/weekly). | Avoids WorkManager/Drift-isolate complexity; documented limitation: no backup while the app is never opened. |
| TD-19 | AI assistant = local deterministic intent engine (English + Gujarati) answering from DB queries. Optional online model (Anthropic Claude API, user-supplied key, opt-in) only *rephrases/explains* figures already computed locally; it receives aggregates, never raw rows, names are included only if the user allows. AI never writes records; it can only *propose* a draft that opens a normal form for user confirmation. | Prompt §20 safety rules. |
| TD-20 | Gujarati input: (a) phonetic transliteration engine (syllable/akshara parser with virama joining, longest-match tokens) applied as-you-type via a composing-word controller; (b) on-screen Gujarati keypad; (c) system keyboard always available. | Not char-by-char replacement; conjuncts produced via virama (U+0ACD) and shaped by the text engine. |
| TD-21 | Configuration through `--dart-define` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `GITHUB_OWNER`, `GITHUB_REPO`). | No secrets in source; CI injects values. |
| TD-22 | Fonts bundled as assets (Poppins + Noto Sans Gujarati, OFL). | Correct rendering offline; no runtime font download. |
| TD-23 | **Light-only, five Gujarati palettes, Rann Utsav default** (owner decisions 2026-11-18 and 2026-11-19, replacing the master brief's green Theme A/B/C). Palettes: Rann Utsav, Neel Gagan, Bandhani Lal, Kesariyo, Patola Rani. Saved removed palettes (Ajrakh Neel, Sindoor, Haldi) fall back to the default. No dark mode, no system option. Green only for money in. Fixed palettes (no Material You dynamic colour). | Consistent cultural identity chosen visually by the owner. `HmColors.accentInk` (= tertiary) added so status text stays ≥ 4.5:1 where the decorative highlight (e.g. Rann silver) would be unreadable. |
| TD-24 | **Gujarati keypad on one page with context rows** (2026-11-19): two suggestion rows show the barakhadi of the consonant before the cursor (incl. half form ્ and ra-conjunct ્ર), otherwise the vowels and an anusvara key; a vowel key forces vowels after a consonant. Logic is a pure function of the text before the cursor. | Owner request: no switching pages to go from ક to કુ; half letters (પુણ્ય, હર્ષ) in two taps. Pure logic is unit-testable; stored text is standard Unicode. |
| TD-25 | **Excel-like transactions sheet** as a second view of the Transactions tab (list ↔ sheet, remembered in settings): oldest first, Income / Expense columns, running balance, totals row; same filters, search and export as the list. | Owner request for an Excel-style view of personal data. Running balance computed in `TransactionSheet` (integer paise, deterministic order) so the last balance equals the period savings. |
| TD-26 | `docs/DATABASE_SCHEMA.md` is generated from Drift's exported schema by `tool/gen_database_schema_doc.dart`. | Column, key, check and index docs cannot drift from the real database. |
| TD-27 | CI on GitHub Actions (format, generated-code, analyze, tests, Supabase SQL tests) and a tag-triggered release workflow that refuses to publish without release signing, verifies the certificate, and publishes the APK with a `.sha256` file in `sha256sum` format. | Matches what the in-app update checker verifies; debug-signed or secret-key builds can never be published. |
| TD-28 | Device tests reuse the app-flow tests (`integration_test/app_flows_test.dart` imports `test/widget/app_flow_test.dart`) plus device-only backup tests. | One set of flows verified on both the host and real Android rendering, without duplication. |
| TD-29 | Account guard in the router: with a cloud configuration and no verified account on the device, every route redirects to the account step (new installs, pre-2026-11-19 installs, sign-out, lost session). Pending sign-up details are kept in `app_settings` until verified. | Compulsory account without losing data; the email link works after an app restart. |
| TD-30 | Guided tour: a spotlight overlay in `MaterialApp.builder` (no extra package), 7 steps across the tabs plus a finish card; sample data created through the normal repositories, in the app language, with its ids recorded; removal deletes only sample records and keeps any sample person or group the user has used. Offered once after the first sign-up, replayable from More. | Owner request for a complete first-run tour with sample data; safe removal; no dependency. |
